# 接客テンプレート ＆ 比較実験の設計

3つのアプローチ型を実地で回し、**どれが一番成果が出るかを数字で判断する**ための設計書。

---

## テンプレート一覧

| | 名前 | 入り方 | 向いている客 |
|---|---|---|---|
| **A** | [観察 → ヒアリング型](A_観察ヒアリング型.md) | 一周させてから、生活を聞く | 単独・じっくり型・警戒心が強い |
| **B** | [試着ファースト型](B_試着ファースト型.md) | 即サイズを聞いて履かせる | 回遊が速い・滞在短そう・混雑時 |
| **C** | [スタイリング起点型](C_スタイリング起点型.md) | 今日の服を褒めて接続する | 服装にこだわりが見える・感度高め |

**すべてのテンプレで [共通ルール](共通ルール.md) は必ず守る。**

---

## 実験設計

### 固定する変数 / 変える変数

| | 内容 |
|---|---|
| **固定**（全テンプレ共通） | クロージング・アップセル・欠品対応の3鉄則 ＋ 開店前チェック |
| **変える**（比較対象） | アプローチ〜試着誘導までの**入り方** |

後半を固定しているのは、**そこが今いちばん穴だから**。
全部を同時に変えると「テンプレの差」なのか「クロージングの出来」なのか分からなくなる。

---

### ⚠️ 割付のルール：**接客ごとにローテーション**

```
1人目 → A
2人目 → B
3人目 → C
4人目 → A
...
```

### 「日替わり」「週替わり」にしてはいけない

曜日・天候・客層が日によって大きく違うため、
**テンプレの差なのか、その日がたまたま良かっただけなのかが区別できなくなる。**

接客ごとに回せば、良い日も悪い日も3テンプレに均等にかかるので、差が出たらそれはテンプレの差。

### 例外：明らかに向かない相手には使わない

- 急いでいる客に A（一周待ち）→ 逃げる
- 服装に無頓着な客に C（褒め）→ 不自然

**無理に割付を守って接客を壊さない。** 飛ばした場合はログに「スキップ・理由」と残す。
（スキップが特定のテンプレに偏るなら、それ自体が「使える場面が狭い」という結果になる）

---

### ⚠️ 店舗が変わる期間の扱い

```
〜10/18     大阪
10/19〜約1ヶ月  東京
11月下旬〜   大阪
```

**店舗が変わると客層も変わる**ので、大阪のデータと東京のデータを単純に足すと濁る。

### 対処

1. **ログに必ず店舗を記録する**（後から分けて見られるようにする）
2. **比較は同一店舗内で行う**
   - 東京期間の A vs B vs C
   - 大阪期間の A vs B vs C
3. 件数が揃えば「**同じテンプレの大阪 vs 東京**」も見られる
   → これは**テンプレの汎用性**が分かる、かなり面白い比較になる

東京1ヶ月は、**まとまった件数を一気に取れるチャンス**。ここでデータの大半が溜まる想定。

## 測る指標

毎回ログに残す。[`../logs/`](../logs/) に月ごとのファイル。

| 指標 | 計算 | 何が分かるか |
|---|---|---|
| **試着率** | 試着に至った数 ÷ 接客数 | アプローチ〜試着誘導の強さ＝**テンプレの差が最も出る指標** |
| **成約率** | 成約数 ÷ 接客数 | 最終的な結果 |
| **試着→成約率** | 成約数 ÷ 試着数 | クロージングの強さ（共通ルールが効いているか） |
| **平均点数** | 総点数 ÷ 成約数 | アップセルが効いているか |
| **連絡先取得率** | 取得数 ÷ 欠品が発生した接客数 | 鉄則3が守れているか |
| **失注理由の内訳** | 在庫 / サイズ / 価格 / 検討 / その他 | **接客の問題か、店舗の問題かの切り分け** |

### 注目すべき点

- **テンプレの差が出るのは主に「試着率」**。入り方を変えているので当然そこに出る
- **「試着→成約率」に大きな差が出たら、それは共通ルールが守れていない接客がある**ということ

## 判断のタイミング

| 件数 | やること |
|---|---|
| 〜10件/テンプレ | **まだ判断しない。** 数字を見ても意味がない |
| 10〜15件/テンプレ | 傾向を見る。**仮説として**書き留める |
| 20件〜/テンプレ | 差が出ていれば採用。マニュアルに昇格 |

**1件や2件で結論を出さない。** 1回うまくいった型を「正解」にしてしまうと、
たまたまの話が社内ルールになり、後から現場が困る。

---

## 運用の流れ

```
接客する（テンプレをローテーション）
   ↓
その場で logs/YYYY-MM_実験ログ.md に1行追加（30秒）
   ↓
印象に残った接客だけ records/ に詳細記録
   ↓
月末に集計 → README の仮説を更新 or 昇格
```

**全部の接客を詳細記録する必要はない。**
ログの1行は毎回、詳細記録は「良かった／悪かったが印象に残った接客」だけでいい。
続かない仕組みにすると、データが溜まる前に終わる。
